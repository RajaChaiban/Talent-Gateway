# BACKEND.md — server-side design

Everything that runs on the server for this app. Today that is sign-in with Supabase Auth, the protected `/app` area, the jobs list, creating a job, the job page with its threshold editor (`PATCH /api/jobs/[id]`) and its resume upload (`POST /api/resumes/sign`, `POST /api/resumes/[id]/complete`, `DELETE /api/resumes/[id]`) and download (`GET /api/resumes/[id]/file`), and the screening pipeline's route handlers (`POST /api/jobs/[id]/analyze`, `GET /api/jobs/[id]/progress`, `POST /api/resumes/[id]/analyze`, `POST /api/resumes/[id]/score-anyway`, section 7), which the job page's Analyze panel and "Score anyway" button call, and the invitation route (`POST /api/candidates/[id]/invite`, section 7), which the candidate detail's "Invite to interview" button calls; each ranked row also has an "Invite to interview" shortcut that only opens that detail. There are no workflows.

**This document describes the code on `main`.** Two rules keep it that way:

- A change to a route, server action, environment variable, model call, error code or `src/lib` folder updates this document in the same pull request. `npm run docs:check` (section 10) fails CI when one of those is added, renamed or removed and this document does not follow.
- Work that is decided but not merged is written only inside a **planned block**: the text between a line holding `<!-- planned:start -->` and a line holding `<!-- planned:end -->`. Nothing in a planned block exists on `main`. When the pull request merges, its text moves out of the block in that same pull request. There is no planned block today.

The section numbers are fixed: `npm run docs:check` finds sections 2, 4, 5, 8 and 9 by number. Fill a section in; do not renumber or remove it.

## 1. Shape of the backend

Next.js on Vercel, with Supabase (Postgres, Auth, Storage) as the system of record. The app holds the anon key only and acts as the signed-in recruiter, so row-level security in the database decides what every query returns.

Data access lives in `src/lib/<feature>/queries.ts`. A query takes the caller's Supabase client instead of creating one, so the page decides whose access rules apply. `listJobs` reads the newest 100 jobs with `resumes(count)` in the same query, and leaves the description out because the list never shows it. The job page reads three things in parallel: `getJobPage` (`src/lib/jobs/queries.ts`: the job, then its candidates (each with its invitation, embedded through the unique `invitations.candidate_id`) and its resumes' ATS columns in parallel, turned by the pure helpers in `src/lib/jobs/helpers.ts` into the ranked candidates, best match first with Radar parsed (`radar.ts`), the set-aside and queued resumes, and the per-bucket counts), `listResumes` (`src/lib/resumes/queries.ts`; id, name, status and date, oldest first, never the text) for the resumes section, and `loadWork` (`src/lib/screening/queries.ts`) for the number of resumes that need work; an id that is not a UUID, or a job the recruiter cannot see, renders the `/app` not-found page. A failed database call throws `JobsDataError` (or `ResumesDataError` for the resumes queries), which the `/app` error boundary turns into a retryable message and a route handler turns into a 500 with a safe message.

Resume upload, on the job page. The recruiter drops or picks PDF and DOCX files; the browser checks each one (type by its declared type, or by its extension when the browser gives none; size; at most 20 per drop and 50 per job) and puts the accepted ones in a queue that runs three at a time. Each file then goes through three steps, and every step is safe to repeat:

1. **Sign.** `POST /api/resumes/sign` checks the job, the name, the type and the size, enforces the 50-per-job cap (counting again after the insert, so requests that arrive together cannot pass it), inserts a `pending` row and returns a signed upload token for `{job_id}/{resume_id}/{safe file name}` in the private `resumes` bucket. The browser chooses the resume id, so signing the same file again after a lost answer names the same row instead of making a second one.
2. **Upload.** The browser sends the file straight to Supabase Storage with that token (`src/lib/supabase/client.ts`, the anon key and the recruiter's session). The file never passes through a Vercel function on upload, so the 4.5 MB function body limit never applies and no function spends time relaying bytes. The bucket itself refuses any type other than PDF or DOCX and anything over 5 MB.
3. **Complete.** `POST /api/resumes/[id]/complete` is the only time the server reads the file: it downloads it with the recruiter's client, judges it by its bytes (a `%PDF-` header, or a zip holding `word/document.xml`), never by its name or declared type, and extracts its text: a PDF with `unpdf`, page by page; a DOCX by inflating its zip under caps (`zip-inflate.ts`) and handing only its XML parts to `mammoth`. In the same pass it counts the file's pictures: for a PDF, the image-painting operations in each page's operator list (image objects, inline images and image masks, including the grouped and repeated forms pdf.js merges them into; nothing is rendered, and the page cap and deadline apply), and for a DOCX, the files under `word/media/`, read from the same checked walk of the archive. A page whose operations cannot be listed fails the read as unreadable, so a picture is never hidden by a count that gave up. The row becomes `extracted` with the text and `image_count`, or `failed` with a reason the recruiter can act on. Extraction is bounded: the 5 MB size, 5 PDF pages, 500 zip entries, 512 KB of DOCX markup and 8 MB inflated in all, and an 8-second deadline. A parser that never yields cannot be interrupted on the same thread; the caps are what bound it.

A failed step is retried with back-off when the failure is transient (a lost connection, 429, 500, 502, 503, 504, honouring `Retry-After`), up to five attempts; a refusal (a wrong type, a file too big, an unknown job, a full job) is final. Downloading a resume (`GET /api/resumes/[id]/file`, linked from each stored row of the resumes section, from the file name in a candidate's detail and from each set-aside resume) reads the row with the recruiter's client, so row-level security decides who may download, then answers 303 to a signed link valid for 60 seconds whose `download` option saves the file under its original name; the bytes come from Storage, not through a function. A `pending` row shows no link, because its upload may never have arrived; `extracted` and `failed` rows were both read back from storage, so they have a file. Removing a resume deletes its stored file first and then its row, so a storage failure leaves a row the recruiter can still see and remove. Storage that answers with a 5xx, a timeout or a rate limit becomes 503 `storage_unavailable` with `Retry-After: 2`; any other storage error is a 500.

The threshold editor on the job page saves each slider when it is released (a run of arrow-key presses waits 500 ms and sends only its last value). Saves for one field go one at a time, last choice wins; a failed save puts the slider back to the stored value and says so beside it.

Writes go through server actions. `createJobAction` parses the form with `createJobSchema` (`src/lib/jobs/schemas.ts`) before it touches the database: the two thresholds arrive on the 0.0 to 10.0 scale and are stored as whole tenths (8.5 is saved as 85), and a value with more than one decimal is rejected, not rounded. When the save fails, the action logs the Postgres error code only and returns the typed text, so nothing the recruiter wrote is lost.

## 3. Auth and access

Supabase Auth, email and password. Sign-ups are disabled on the Supabase project, so only the demo user can sign in. The session lives in cookies set by the server client.

- `/login` is the only page that signs people in. `/` and the sample files under `/samples/` are public: `/samples/*` is outside the proxy matcher, so the proxy never runs for it and a signed-out visitor gets the file. Everything under `/app` needs a signed-in user.
- Two checks protect `/app`. The proxy (`src/proxy.ts`, on `/app/**` and `/login`) refreshes the session and redirects page navigations: signed out on `/app` goes to `/login?next=...`, signed in on `/login` goes on to `next`. Then every `/app` page calls `requireSignedInUser()` itself, because the proxy is only a first check and a layout does not gate its pages.
- API routes (`/api/**`) are also in the proxy matcher, so a `fetch` from the app refreshes the session, but the proxy never redirects them. Each route handler calls `requireUser()`, which asks Supabase Auth and answers JSON instead of redirecting: 401 `unauthorized` when signed out, 503 `auth_unavailable` when Supabase Auth cannot answer. A handler that changes data then calls `requireSameOrigin()`, which refuses with 403 `forbidden` any request not sent by this app's own pages (`Sec-Fetch-Site: same-origin`, or an `Origin` equal to the request's own scheme and host), so another site cannot use the recruiter's cookies to change data.
- When Supabase rejects a session that the cookie still claims, the page redirects to `/auth/signed-out`, which clears the cookies so the proxy cannot bounce the browser back. When Supabase Auth cannot answer at all, the page shows a retryable error instead of signing the user out.
- Sign-out ends only this browser's session (`scope: "local"`), because the demo login is shared.
- Who is signed in is always asked from Supabase (`auth.getUser()`), never read from the unverified cookie.
- After sign-in the browser goes to the `next` path, which is accepted only when it is a path on this site; anything else becomes `/app`.
- A failed sign-in says "Email or password is incorrect", never which of the two was wrong.

## 5. Model calls

Two calls, both through the AI SDK to Vercel AI Gateway. Only the screening pipeline (`analyzeResume`, section 7) calls them, in parallel, for a resume that passed or was overridden past the ATS gate.

| Key | Model | Function | Returns |
|---|---|---|---|
| `AI_MODELS.scoring` | `anthropic/claude-haiku-5.5` | `scoreResume` (`src/lib/ai/score-resume.ts`) | Candidate name, a role match, a start score and part-scores on the 0 to 10 scale (from which the code adds up the match score), summary, strengths, gaps |
| `AI_MODELS.radar` | `anthropic/claude-haiku-5.5` | `runRadar` (`src/lib/ai/run-radar.ts`) | Four risk flags, each with a one-line note: copied text, employment gaps, job hopping, AI-written padding |

- **Gateway and credentials.** A model is a plain `provider/model` string from `AI_MODELS` in `src/lib/config.ts`, which the AI SDK sends to AI Gateway. The gateway is authenticated by the project's OIDC token (`VERCEL_OIDC_TOKEN`, supplied by Vercel at run time and by `vercel env pull` locally), so the app holds no provider key. Changing a model or a provider is a one-line config change.
- **Structured output.** Both calls go through `generateStructured` (`src/lib/ai/generate.ts`): `generateText` with `Output.object({ schema })`, so the answer is parsed against a Zod schema (`src/lib/ai/schemas.ts`) and never read as free text. An answer that does not parse is retried once; a second failure fails that resume instead of guessing.
- **The match score is added up in code.** The scoring model classifies and gives small part-scores, all on the 0 to 10 scale with at most one decimal, and never returns a total: `role_match` (`same`, `related` or `unrelated`, from the most recent position, by its title or by the work described under it), `start_score` (0 to 5), `must_haves` (1 to 12 items, one per must-have of the job description, each `shown`, `equivalent`, `listed` or `missing`), `evidence` (0, 0.5 or 1), `proof_of_work` (0, 0.3 or 0.6) and `education` (0, 0.2 or 0.4). An answer outside these ranges fails the schema. `totalScore` (`src/lib/ai/total-score.ts`, pure) adds them up with the weights in `SCORE_WEIGHTS` (`src/lib/config.ts`) and turns the total into stored tenths with `toStored`:

  | Part | Rule |
  |---|---|
  | Start | `same`: exactly 5.0 whatever the model wrote; `related`: the model's value clamped to 2.5 to 4.0; `unrelated`: clamped to 0 to 1.5 |
  | Skills | 3.0 x (shown x 1 + equivalent x 0.5 + listed x 0.25) / the number of must-haves |
  | Evidence, proof of work, education | The model's values, clamped to 0 to 1, 0 to 0.6 and 0 to 0.4 |
  | Total | start + (skills + evidence + proof of work + education) x start / 5, rounded to one decimal |

  A resume whose most recent title is the job's role therefore scores 5.0 to 10.0, one that starts lower earns the additions in proportion, and an unrelated one stays at 3.0 or below. `scoreResume` returns the name, the total as stored tenths, the summary, strengths and gaps, plus the breakdown for the model evaluation; the breakdown is not saved.
- **Limits (`SCREENING_AI_LIMITS`).** One call, with its parse retry and the SDK's one transport retry, shares a single 25 second abort budget. The job description is cut at 8,000 characters and the resume at 12,000 before sending, and Radar compares at most 8 other resumes as 600-character excerpts, so the cost of a call is bounded whatever was uploaded.
- **Rate limits.** A 429 from the gateway becomes `ModelBusyError` with the seconds to wait. It is retryable: the resume is not marked failed, and the route answers 503 `model_busy` with `Retry-After`.
- **Prompts.** The resume and the job description are sent as clearly delimited sections and the instructions tell the model to treat them as data, so text inside a resume cannot act as an instruction. Radar excerpts leave out the header lines of other resumes, so one candidate's contact details are not sent with another's.
- **Tests never call a model.** Unit tests use the AI SDK's mock model. For browser tests, `E2E_FAKE_MODEL=1` makes `resolveModel` return a local stand-in, and it is refused on any Vercel deployment (`standInAllowed`), so production can only ever use the real gateway model.

## 7. Screening pipeline

One resume at a time, through `analyzeResume` (`src/lib/screening/analyze.ts`), which `POST /api/resumes/[id]/analyze` and `POST /api/resumes/[id]/score-anyway` call. It is the only module that imports `scoreResume` and `runRadar`; `src/lib/screening/boundary.test.ts` fails if anything else does, so no caller can reach a model without the ATS gate running first. The one exception is outside the app: the model evaluation's `evals/model-call.ts` (section 10), which runs the ATS check itself before it scores a local file. Everything runs with the recruiter's client, so row-level security applies.

1. **Load.** The resume and its job; an unknown id is a 404.
2. **Already scored.** A resume that has a candidate row answers `scored` with no model call and no write. This is what makes a repeated run cost nothing.
3. **No text.** A resume without extracted text (still uploading, or its upload failed) answers `not_extracted` and is not touched.
4. **ATS gate.** `checkAts` (below) runs on the text and the file facts (the type from the file name's extension; the upload already checked the real type), and the result is saved to `resumes.ats_status`, `ats_score` and `ats_reasons` before any model call. The gate is read back from the saved row: `NOT_ATS_READY` without `ats_override` answers `ats_failed` and makes **zero** model calls.
5. **Model calls.** `scoreResume` and `runRadar` run in parallel (Radar gets up to 8 of the job's other resumes with text, oldest first, as excerpts for the copycat check). When one fails the other is aborted.
6. **Save.** One `candidates` row: the name (the file name without its extension when the model gives none), the match score in tenths (added up in code from the model's parts, section 5), summary, strengths, gaps, Radar results, the first email address in the resume text (lower case; null when there is none) and `invite_status = 'NONE'` whatever the score. Only a recruiter's click invites anyone. The insert is an upsert on `(job_id, resume_id)` that does nothing on conflict, and a clash on the unique `resume_id` is treated the same way, so two simultaneous calls for one resume make one candidate and both answer `scored`.

**Failures.** A model error (an answer that fails its schema twice, a gateway error) is logged once without resume text and marks the resume `status = 'failed'` with its text kept, which is how an analysis failure differs from an upload failure; the route still answers 200 with `status: "failed"`, so the browser's queue moves on, and the next run retries it. A resume that has a candidate is never left failed, whatever order two racing calls finish in. A **429 from the gateway** is not a failure: it throws `ModelBusyError`, nothing is written, and the route answers 503 `model_busy` with `Retry-After` so the browser tries that resume again later. A database failure is a 500.

**A run and the job's status.** `POST /api/jobs/[id]/analyze` lists the resumes that need work, puts earlier analysis failures among them back to `extracted`, and sets the job to `ANALYZING` (`DONE` when the list is empty). The browser then calls the per-resume route for each id, one request per resume, so each function stays short (at most two parallel model calls with a 25 second budget each, inside a 60 second `maxDuration`). After every per-resume call, and on every `GET /api/jobs/[id]/progress`, the job is settled from its rows (`settledStatus` in `work.ts`): a job in `ANALYZING` with nothing remaining becomes `DONE`, or `ERROR` when every resume with text failed. Because the status is derived from what is saved, a run the browser abandoned, a retried call or calls finishing out of order still end in the right state. "Score anyway" sets the job back to `ANALYZING` before it runs and settles it after.

Re-running a job whose resumes are all scored or set aside lists nothing, makes no model call and creates no row.

**The browser's side of a run (the Analyze panel).** The job page's Analyze panel (`src/app/app/jobs/[id]/analyze-panel.tsx`) calls `POST /api/jobs/[id]/analyze`, then hands the returned ids to the analyze queue (`src/lib/screening/analyze-queue.ts`, a pure module with no DOM or React). The queue keeps at most `ANALYZE_QUEUE_LIMITS.concurrency` (3) per-resume requests in flight; a 429, a 503 (`model_busy`) or a network failure is retried up to `maxAttempts` (5) times, waiting the `Retry-After` value when the server sends one and otherwise an exponential back-off from 1 second with jitter, never more than 30 seconds; any other error fails that resume without a retry, and `failed` from the route counts as failed. Leaving the page stops the queue and aborts the requests in flight. While it runs, the progress bar reads `GET /api/jobs/[id]/progress` at most every 500 ms and the page refreshes at most every 2 seconds, so new candidates appear as they are scored; the bar shows the server's counts, not the queue's tally. "Retry failed" sends the failed ones again. Opening a job still in `ANALYZING` (a run whose tab was closed) reads progress once, which settles the job if nothing remains. The "Not ATS-ready" tab lists each set-aside resume with its ATS score and reasons, and its "Score anyway" button calls `POST /api/resumes/[id]/score-anyway` (`score-anyway-client.ts` turns the answer into a message); an overridden resume that still has no score is listed under "Queued for scoring" on the Ranked tab.

**Invitations.** Nothing invites a candidate automatically: a score above the invite bar only highlights who to review. In the candidate detail on the job page, the invite panel (`src/app/app/jobs/[id]/invite-panel.tsx`, a client component) shows an email field filled in with the address read from the resume, which the recruiter can correct because the first address in a resume can be a referee's. Each ranked row's header also carries an "Invite to interview" button ("Try again" after a failed send, none once sent, where the row shows "Invited"); it is a sibling of the expand trigger, sends nothing, and only opens that candidate's detail and moves focus to the "Candidate email" field, scrolled into view. Clicking the panel's own "Invite to interview" calls `POST /api/candidates/[id]/invite` (`invite-client.ts` turns the answer into a message) and refreshes the page; the click is the approval. `inviteCandidate` (`src/lib/invitations/invite.ts`) inserts the `invitations` row (`approved_by`, `approved_at`, `sent_to`), sets `candidates.invite_status` to `APPROVED`, sends, then records `sent_at` and `message_id` with `SENT`, or `error` with `FAILED`. `candidates.email` is never changed; `sent_to` records the address used. The email must go out at most once:

- `unique (candidate_id)` makes the insert the lock: of two simultaneous clicks only one inserts, and the other does not send.
- A row with `sent_at` is never sent again; the route answers 200 with the stored state, ignoring the address in the body.
- "Try again" is accepted for `FAILED`, or for `APPROVED` older than 2 minutes (`INVITE_LIMITS.staleApprovalMs`), a send whose request died part-way; the route's 30-second `maxDuration` means no request can still be sending by then. The retry claims the same row in one guarded write (new approval, corrected address, error cleared), so two retries at once send once.
- `APPROVED` younger than 2 minutes is a send in progress: 409, no send.
- The invitation row is written before the candidate's status at each step, so the row decides what happens next.

All delivery goes through `sendInvitationEmail` (`src/lib/invitations/send.ts`), which takes the recipient, subject, text and the invitation id. Email delivery stays outside this app, and that function is the only place it happens:

- **With `RESEND_API_KEY` set**, the email is sent through Resend in one HTTPS request (`POST https://api.resend.com/emails`), with no mail library. The sender is `INVITE_FROM_EMAIL`. The invitation id goes in the `Idempotency-Key` header, so a request the app repeats is delivered once. The request is abandoned after 10 seconds. The id Resend returns is stored in `invitations.message_id`. A refusal throws with the status and Resend's reason, never the key; the candidate becomes `FAILED` and the route answers 502 `email_failed`.
- **With `INVITE_REDIRECT_TO` set**, every invitation is delivered to that one inbox and the subject starts with `[to: <approved address>]`. `invitations.sent_to` still records the address the recruiter approved. It is for a deployment without a sending domain: Resend's test sender (`onboarding@resend.dev`) delivers only to the account owner's own address. The deployed app does not set it: it sends from a verified domain (`hiring@talentgateway.dev`), so an invitation reaches the address the recruiter approved. The sample resumes carry made-up addresses, so a reviewer types a real one in the email field before approving.
- **Without `RESEND_API_KEY`**, the function is a stand-in outbox: it delivers nothing and returns `outbox:<invitation id>`. Unit tests run this way, so no test can mail a real person.

Changing the provider means changing that one function. The candidate detail shows the email that was produced, rebuilt by the same pure function (`message.ts`) from the candidate's name and the job title. The send runs inside the request; there is no workflow, and the 2-minute rule covers a request that died between approval and send.

**Pre-screen (`checkAts`, `src/lib/ats/check-ats.ts`).** A pure function over a resume's extracted text and its file facts. It calls no model and no network, so a resume it sets aside costs nothing. Every threshold and weight comes from `ATS_CONFIG` in `src/lib/config.ts`, which is validated before use (an invalid config throws an error naming the field).

| Check | Passes when | Required | Weight |
|---|---|---|---|
| `readable_text` | The text has at least the configured number of readable characters (a scan or a broken file fails here) | yes | 15 |
| `contact_info` | An email address is found in the text | yes | 15 |
| `phone` | A phone number is found in the text: a run on one line of digits, spaces and phone punctuation holding 9 or more digits (`src/lib/ats/phone.ts`, the same rule the prompt code uses to strip and match phone numbers). A date range such as "2015 - 2019" holds 8 and is not one, and two date ranges on stacked lines are never joined | yes | 10 |
| `standard_sections` | Enough of the standard section headings appear | no | 25 |
| `layout_noise` | The share of stray symbols in the text is under the limit | no | 20 |
| `file` | The file is a supported type and an acceptable size | yes | 5 |
| `picture` | The file holds no more than `maxImages` (0) pictures, as counted at extraction and saved in `resumes.image_count`. A row with no count (null) passes | yes | 10 |

Every check always runs, in the order above. The result is `ATS_READY` only when every required check passes and the weighted score reaches the pass score (6.0); otherwise it is `NOT_ATS_READY` with one plain-language reason per failed check, for example "No phone number was found in the text, ..." or "The file contains 2 pictures. A photo or graphic cannot be read by an applicant tracking system." A missing email, a missing phone number or a picture therefore sets the resume aside whatever its score, and no model is called unless the recruiter uses "Score anyway". The weights add up to 100. The score is stored in tenths like every other score.

Known limits: any picture counts, so a logo, an icon or a decorative line saved as an image sets the resume aside like a photo (the recruiter can use "Score anyway"); in a PDF, a picture repeated in one run of drawing operations counts once. A phone number written in words or with fewer than 9 digits is not found.

## 8. Environment variables

Set in `.env.local` for local work (git-ignored) and in the Vercel project for deployments. There is no `.env.example`, because `.gitignore` excludes every `.env*` file; this table is the list.

| Name | Scope | Source |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | browser and server | The Supabase project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | browser and server | The Supabase anon key. Public by design: row-level security decides what it can read |

| `INVITE_REDIRECT_TO` | server | Optional. When set, every invitation is delivered to this one inbox instead of the candidate's address. Remove it to send to candidates, which needs a sender on a verified domain |

## 9. Errors and limits

Every route handler error has the body `{ "error": { "code": ..., "message": ... } }` (`jsonError` in `src/lib/http.ts`). Messages are safe to show: a database error is logged by its Postgres code only (`logServerError`) and never sent.

| Code | Status | When |
|---|---|---|
| `invalid_input` | 400 | The id is not a UUID, the body is not JSON, or a field fails its schema; the message names the field |
| `unauthorized` | 401 | No valid session |
| `forbidden` | 403 | A state-changing request that did not come from this app's own pages |
| `not_found` | 404 | No job, resume or candidate with this id, or row-level security hides it |
| `conflict` | 409 | The job already holds 50 resumes; a resume id is already used for a different file; the file to complete is not in storage yet; "Score anyway" was asked for a resume that is already scored or was not set aside; or an invitation for the candidate is being sent right now |
| `payload_too_large` | 413 | The declared file size is over 5 MB |
| `unsupported_media_type` | 415 | The declared file type is not PDF or DOCX |
| `email_failed` | 502 | The send function failed for an invitation; the error is recorded on the invitation, the candidate is `FAILED`, and "Try again" reuses the same row |
| `server_error` | 500 | A database call failed, or storage refused a call for a reason other than being busy |
| `auth_unavailable` | 503 | Supabase Auth could not answer; try again |
| `storage_unavailable` | 503 | Supabase Storage could not be reached, timed out, was rate limited or answered with a 5xx; sent with `Retry-After: 2` |
| `model_busy` | 503 | AI Gateway rate-limited a model call; sent with `Retry-After` (the gateway's value, 1 to 60 seconds, 5 when it gives none). The resume is not marked failed |

A file the server could read but not accept (empty, not really a PDF or DOCX, a Word file named `.pdf` or the other way round, damaged, password-protected, over a size, page or markup cap, or past the 8-second read deadline) is not an error response: `complete` answers 200 with `status: "failed"` and a message, and the row is saved as `failed`.

### Model evaluation (`npm run eval`)

The scoring model is judged against a fixed set instead of by eye (design: `docs/specs/pre-screen-and-evals.md`, section 5; what each test means and every report: `docs/evals/README.md`).

- **What it calls.** `scoreResume` itself, so a run uses the app's scoring prompt, schema, `SCREENING_AI_LIMITS` and AI Gateway path. `evals/model-call.ts` is the only file outside the pipeline that imports it; `src/lib/screening/boundary.test.ts` holds `evals/` to that one file and four AI-layer modules, with no generation function of its own. It skips the pipeline's ATS gate on purpose: the written resumes are built to pass it (a unit test checks they do), and every local file goes through the real `extractText` and `checkAts` first, so a file that is set aside is never sent.
- **The set.** Seven job descriptions (Software Engineer, a stack-flexible version of it, Finance Manager, Applied AI Engineer, Registered Nurse, Digital Marketing Manager, Account Executive) and written resumes of invented people under `evals/` (role match with a role floor of 5.0 for same-role cases, five one-factor pairs, the same resume against the strict and the stack-flexible job, an injection attempt), with their expectations typed in `evals/cases.ts`. Test 8 (job types, `evals/job-types.ts`) scores five resumes (strong, mid, vague, related, unrelated) against each of five kinds of job, each against a stated score range, with the order within each job and a filtering check that needs no model: every one of the 25 texts must be `ATS_READY` through the real `checkAts`, and four negatives built from one of them (no email, no phone number, both, one picture) must each be set aside on exactly that check. Tests 1 and 2 also read labelled PDF and DOCX files from a local folder that is never committed (`Resume_test/dummy` by default, `--files <dir>` to change it), and score the ready ones against the Applied AI Engineer job; a file's expectation comes from its name, and the run skips those tests with a note when the folder is missing. A report names local files by file name, ATS status, failed checks and score only.
- **Score bars.** Test 7 makes no model call: `evals/bars.ts` applies a job's two bars to the scores already collected, with the app's `isTopTalent`, under three settings (the default from `JOB_THRESHOLD_DEFAULTS`, a strict and a lenient one). Only the default is graded. It holds every case that states a band, and the test 8 cases whose range lies inside one band (strong and unrelated). The bars are not part of the scoring prompt, as in the pipeline, so moving a bar re-labels candidates without re-scoring them.
- **How it runs.** `node evals/launch.mjs run` (`npm run eval`) loads `evals/run.ts`, and `node evals/launch.mjs compare` (`npm run eval:compare`) loads `evals/compare-run.ts`, through Vite's server-side module loader from `vitest/node`, which compiles TypeScript and resolves `@/` like the unit tests, with no dev server and no extra dependency. Three calls run at once; a gateway rate limit (the `ModelBusyError` rule, `rateLimitRetryAfter`) is retried up to four attempts with back-off, and a call that still fails is graded as an error. `--model <slug>` sends the scoring call to another gateway model for that run only (through the AI SDK's global default provider in the runner's process); `--label <text>` names the report; `--runs <n>` sets the runs per stability case (default 3); `--only <n[,n...]>` runs only the listed tests (for example `--only 8`, 25 calls), and the measures of the tests that did not run are reported as skipped, not failed. Token usage per call comes from the AI SDK's global telemetry hook (`registerTelemetry`), and the price from the gateway's model list.
- **Output.** A table on the console and `docs/evals/<yyyy-mm-dd>-<label>.md` with the date, model, prompt version (a short hash of `SCORE_INSTRUCTIONS`), the tests that ran, every case with its expected and actual result, how each score was added up (role match, start, skills, evidence, proof of work, education, total; a written case also lists its must-haves with their statuses, a local file only counts them), each measure with pass or fail, the failing cases, the score bars table, a table per test 8 job, speed and tokens. Next to it, `docs/evals/<yyyy-mm-dd>-<label>.json` (`evals/scores-file.ts`) holds the model, prompt version, date, label, tests run, cost, median seconds and every case's score, role match and parts, with no resume text, name or must-have. `npm run eval:compare -- <a.json> <b.json>` makes no model call: it writes `docs/evals/<yyyy-mm-dd>-compare-<labelA>-vs-<labelB>.md` with each shared case's two scores and difference, the mean absolute and largest difference, the count over 1.0, whether every test 8 job keeps the same order, and both runs' cost and median speed. Every score, band, margin and bar is shown on the 0.0 to 10.0 scale through `src/lib/score.ts`; the grading keeps stored tenths. `docs/evals/README.md` lists every report and every comparison. The exit code is 1 when a pass mark is missed and 2 for a usage or setup error.
- **Credentials.** The runner reads `.env.local` itself (without printing it) for `VERCEL_OIDC_TOKEN` from `vercel env pull`, or uses `AI_GATEWAY_API_KEY` when that is set in the shell. With `E2E_FAKE_MODEL=1` the stand-in model answers instead, which checks the runner but says nothing about the model.
- **Not in CI**: it needs the gateway token, costs money and is not perfectly repeatable. It is run by hand before a change to the scoring prompt, a limit or the model is merged, and the report is committed with that change. Its pure parts (arguments, file-name expectations, test selection, grading, the test 8 filtering check, report rendering, the scores file, the comparison, the retry pool and the set itself) have unit tests under `evals/` that run in `npm run test` and never call a model.

### Document check (`npm run docs:check`)

`scripts/check-backend-doc.mjs` reads the source tree and this document, with no network and no dependencies, and exits non-zero with one line per problem (each with a "Fix:" hint). It fails when:

| | Source | Must be in this document |
|---|---|---|
| a | Every HTTP method exported by a `route.ts` under `src/app` | A row with that method and path in the section 4 table. A row for a route that does not exist also fails |
| b | Every function exported by a file that starts with `"use server"` | Its name, anywhere outside a planned block |
| c | Every variable in the `src/lib/env.ts` schema and in `.env.example` | Its name in section 8. A name in the section 8 table that nothing defines or reads also fails |
| d | Every folder directly under `src/lib` and `src/app/api` | A line in the section 2 tree. A tree line whose path does not exist also fails |
| e | Every key of `AI_MODELS` in `src/lib/config.ts` and its model string | `AI_MODELS.<key>` and the string in section 5. Skipped while there is no `AI_MODELS` object |
| f | Every member of an exported `...ErrorCode...` union or `...ERROR_CODES...` list under `src/` | The code in backticks in section 9 |
| g | A route's `maxDuration` | Equal to the number after `maxDuration` in its section 4 row, when the row states one |

**What it cannot do.** The check only proves that a thing is *named* in the right section. It does not read the prose, so a wrong description of a route still passes. Keeping the prose right is the job of the author and the reviewer of each pull request.
